# 教培智能客服项目设计稿

## 1. 项目定位

本项目的长期目标是建设一个面向教培场景的全链路内部坐席辅助系统。

第一阶段不直接追求全自动客服，而是以在读服务场景为切入口，先建设一个以离线回放为起点的双台联动系统：

- 面向坐席的辅助工作台
- 面向管理与质检的指挥台

该系统的核心不是“替代人工回答”，而是通过评估、辅助、记录三类能力，帮助团队更稳定地理解对话状态、识别风险、沉淀结构化经验，并为后续学习进化打下基础。

## 2. 一期总体目标

一期聚焦以下目标：

- 以在读服务场景为第一落点
- 以消息分流和坐席辅助为能力优先级
- 以离线回放作为首发验证方式
- 以半自动执行作为介入深度
- 以双台联动作为产品形态
- 以来源标注和完整记录作为演化底座

其中，课程规则、流程说明、知识准确性等内容更多由 RAG 提供支持；系统本身更关注路由、状态识别、辅助提示、复盘与演化结构。

## 3. 一期系统分层

### 3.1 评估系统

评估系统负责看懂一段对话发生了什么，并输出可解释、可追溯的结构化结果。它主要负责：

- 识别意图与服务场景
- 识别建议分流方向
- 识别客户情绪变化
- 识别服务人员状态变化
- 识别对话注意力变化
- 识别压力状态变化
- 识别关键风险节点
- 生成结构化摘要与建议动作候选

评估系统输出的是结构化评估结果，而不是面向最终页面的展示文本。

其中，像“注意力变化”这类仍可能持续演进的信号，不应与意图、路由、风险等基础结构硬绑定，而应作为可独立研究和迭代的信号模块接入评估层。

### 3.2 辅助系统

辅助系统负责把评估系统输出翻译成不同角色可消费的产品能力：

- 给坐席工作台提供建议、提醒、摘要、风险态势和转派辅助
- 给管理与质检指挥台提供全局监控、异常分布、波动趋势和复盘入口

辅助系统不负责定义判断真相，而是负责消费评估结果，并按角色组织提示方式、展示方式和频率。

### 3.3 记录系统

记录系统负责沉淀会话事实、系统判断、来源证据、人工反馈和最终处理结果。它既服务于复盘，也服务于后续评估优化和学习进化。

### 3.4 分层原则

系统采用以下分层原则：

- 评估与辅助分离
- 数据结构与界面呈现分离
- 路由结构与具体渠道分离
- 学习闭环结构与学习效果分离
- 配置优先设计，优先通过配置而不是硬编码处理局部耦合

这个分层是一期最重要的架构骨架之一。

## 4. 一期能力边界

### 4.1 一期明确要做的能力

- 对历史或模拟对话进行离线回放
- 提供 CLI 与 API 形式的核心服务能力
- 提供对话模拟器，用标准协议输入带时间戳的对话事件流
- 识别意图、服务场景、分流方向和关键风险节点
- 识别客户情绪、服务人员状态、注意力变化和压力状态变化
- 为坐席生成辅助建议、摘要、提醒和转派辅助
- 为管理和质检提供全局态势、异常聚合和复盘视图
- 完整记录过程数据、结果数据和来源信息
- 为后续反馈学习预埋结构化接口

### 4.2 一期暂不做的能力

- 不直接接入实时生产会话
- 不在一期内自动办理复杂业务流程
- 不把 RAG 当作系统唯一核心
- 不在一期内完成强自适应学习闭环
- 不把一期 UI 当作最终生产级坐席前台来建设

一期重点是把结构搭稳、边界理清、记录打透，而不是把所有能力一次性做满。

## 5. 一期数据流与接口边界

一期建议采用如下主链路：

`对话回放输入 -> 评估系统 -> 结构化评估结果 -> 辅助系统 -> 双台呈现 -> 人工处理结果与反馈回写`

### 5.1 评估系统输出对象

评估系统应输出标准化事件或结论，例如：

- 意图分类结果
- 路由建议结果
- 情绪变化事件
- 服务状态变化事件
- 注意力偏移事件
- 压力状态变化事件
- 风险提醒事件
- 当前阶段判断
- 摘要与建议动作
- 来源、证据片段、置信度、触发时点

### 5.2 系统接口边界

建议一期至少定义以下接口边界：

- 会话输入接口
- 评估结果接口
- 反馈回写接口
- 查询与聚合接口

这些接口的目标是让评估层、辅助层、记录层能够独立迭代，避免后续重新耦合。

### 5.3 配置优先设计

一期应坚持配置优先设计，尤其在局部耦合不可完全避免时，优先通过配置抽离变化点，而不是把变化逻辑直接固化在流程代码中。

优先配置化的对象包括：

- 路由节点与路由映射
- 提示阈值与升级条件
- 压力状态灯分级规则
- 来源优先级与来源解释模板
- 提示频率、去重与抑制策略
- 不同场景下的辅助展示策略

配置优先的目标不是把所有问题都变成配置，而是用配置吸收局部变化，维持整体结构稳定。

一期采用代码同源的配置治理方式，这里的“随代码走”明确指默认配置或基线配置。也就是：

- 默认配置和代码、Spec、测试一起受版本管理
- 默认配置定义系统基线行为
- 一期所有核心配置先收紧为基线配置
- 同时预留通用覆盖机制，但不急着展开后台在线配置

### 5.4 配置治理约束

为了避免“配置优先”演化为“配置失控”，一期至少要具备以下治理约束：

- 配置 schema 校验
- 配置变更的测试验证
- 配置版本记录与回滚能力
- 配置与 Spec 的一致性检查

默认情况下，不同信号的消费控制采用“固定档位为主，分层开关兜底”的方式控制复杂度。也就是优先使用少数预设档位承载差异，只有在少数高级场景下才下沉到细粒度开关。

## 6. 一期 Service 交付与使用形式

### 6.1 一期交付形态

一期建议采用：

`CLI / API 优先 + 对话模拟器 + 轻量 Web 控制台`

也就是把系统先做成一个可调用的 headless service，再配一个轻量可视层用于验证和复盘。

### 6.2 CLI 与 API 的定位

- CLI 用于本地回放、批处理、测试驱动、样本验证
- API 用于统一输入输出协议，为后续接入桌面端、插件、Web 客户端预留稳定接口

这种做法的核心价值在于，先把评估、辅助、记录、来源追溯和反馈闭环做成与具体客户端解耦的能力层。

### 6.3 对话模拟器

一期应设计一个对话模拟器，用于输入或回放带时间戳的对话事件流。它可以作为：

- 路由验证入口
- 上下文组织验证入口
- 提示与事件触发验证入口
- 记录与反馈闭环验证入口

对话模拟器的目标不是伪造完整业务世界，而是为一期提供稳定、可重复、可测试的输入面。

模拟器本身也应与具体客户端或 UI 形态解耦，它服务的是协议验证、信号验证和闭环验证，而不是某个前端外壳。

### 6.4 协议演进原则

一期先建立一个可运行的基线协议，但协议不应与当前信号集合硬绑定。协议采用“版本号 + 扩展槽”的方式持续演进：

- 核心字段保持稳定
- 新信号、实验字段、附加上下文优先进扩展区
- 当扩展内容成熟后，再决定是否进入下一版核心协议

这样既能保证一期有稳定输入面和输出面，又不会因为实验信号变化导致整体协议频繁推翻。

当扩展槽字段成熟并进入下一版核心协议时，采用分层兼容策略：

- 对核心审计、复盘、追溯相关字段，优先保证兼容读取
- 对实验字段，不强求历史回填
- 通过读取层和视图层做兼容兜底

目标是不因为协议升级破坏核心复盘能力，同时避免实验字段把历史迁移成本推得过高。

### 6.5 轻量 Web 控制台

一期 UI 更适合定位为轻量 Web 控制台，而不是正式生产坐席端。它主要承担：

- 对话回放
- 评估结果查看
- 来源追溯
- 异常观察
- 管理与质检复盘

它的定位更接近：

- 验证台
- 观察窗
- 复盘台
- 调试控制台

### 6.6 后期 UI 策略

后期进入真实业务接入阶段后，UI 可以优先考虑采用成熟的数据中台、运营中台或管理后台框架，而不是从零搭建完整前台系统。

这样做的价值在于：

- 保持核心 service 独立
- 避免 UI 反向绑架领域结构
- 将主要研发投入集中在路由、评估、上下文、反馈闭环等核心能力上
- 未来可按接入环境替换前端壳，而不重做核心能力

### 6.7 本节原则总结

`核心能力做成可调用服务，验证界面轻量化，生产界面后置并可借助中台框架承载。`

## 7. 提示呈现原则

### 7.1 状态化优先

常规提示不应以大段文字为主，而应以状态化、仪表盘式的方式表达当前会话状态。优先使用：

- 图表
- 数值
- 状态灯
- 趋势线
- 阶段历史

界面应先回答“当前处于什么状态、正在往哪里变化、之前经历过什么”，再提供文字解释。

### 7.2 常规提示与特别警告分层

常规提示以持续可见、低打扰的方式存在，可采用滚动显示、侧边状态区或时间线方式呈现。

特别警告只在高风险事件触发时显著提示，例如：

- 客户情绪快速恶化
- 投诉或流失风险明显升高
- 关键诉求长时间未被回应
- 处理承诺明显偏差

### 7.3 提示策略原则

- 默认状态化展示，不堆文字
- 常规提示滚动显示，不主动打断
- 特别警告显著提示，但必须稀缺
- 先看趋势和阶段，再看单点判断
- 所有提示都应可追溯来源

### 7.4 压力状态灯

系统应设计一个独立的压力状态灯，用于表达当前会话的综合处理压力。它不是单纯情绪指标，而是综合以下因素后的运营信号：

- 客户情绪是否持续恶化
- 会话是否反复拉扯且难以收束
- 是否出现投诉、催促、质疑、不信任
- 坐席是否持续未命中核心诉求
- 注意力是否偏移且未拉回
- 是否接近升级、转派或流失风险

压力状态灯建议采用分级结构，例如：

- 绿灯：压力低
- 黄灯：压力上升
- 橙灯：进入高压区
- 红灯：高风险，需要重点介入

常态下它应常驻显示，只有在状态跨级跃迁时才触发更显著提醒。

## 8. 独立信号与消费解耦

一期应明确区分“信号生产”和“信号消费”。

### 8.1 独立信号模块

像“注意力变化”这类仍需要持续研究和优化的信号，应作为独立信号模块存在：

- 允许先进入系统
- 允许进入记录、回放与反馈闭环
- 不要求一开始就在定义层面写死其业务影响

### 8.2 消费侧配置

信号是否参与下列层次，不由信号定义直接写死，而由消费侧配置决定：

- 是否记录
- 是否展示
- 是否提示
- 是否参与核心路由
- 是否参与综合判断

默认采用少数固定档位控制复杂度，例如：

- 观察型
- 提示型
- 决策参与型

只有在少数高级场景下，才通过分层开关进行更细控制。

### 8.3 信号反馈原则

一期的原则不是“信号成熟后再进入系统”，而是“先让信号进入系统，再通过反馈优化它是否、以及如何影响关键判断”。

### 8.4 生命周期与转换规则

一期为独立信号定义两条解耦轴：

- 消费档位：观察型 / 提示型 / 决策参与型
- 生命周期状态：实验中 / 已验证 / 已冻结 / 已退役

这里需要明确区分：

- 消费档位回答“这个信号当前影响多大”
- 生命周期状态回答“这个信号当前成熟到什么程度”

运行时系统对信号是开环的，不自动决定升级、降级、冻结或退役；这些状态变化由学习/验证系统与人工审核组成的大闭环决定。

### 8.5 升级、降级与退出原则

信号状态变化采用混合治理方式：

- 小升级：规则门槛 + 人工确认
- 重大变更：验证报告 + 人工签核

档位升级按消费层级分层：

- 观察型 -> 提示型：门槛相对较宽
- 提示型 -> 决策参与型：门槛更严格

生命周期进入“已验证”时，至少同时看以下组合证据：

- 人工标注一致性
- 规则或模型产出稳定性

必要时再辅以反馈闭环有效性作为补充证据。

退出机制采用分级退出，而不是一次失败就直接移除：

- 轻度问题先降为观察型或冻结
- 持续多轮验证仍不达标，再进入退役

对于像“注意力变化”这类研究型信号，还应有明确的验证退出规则：若某信号在小样本验证中连续多轮达不到一致性门槛，则至少降为观察型或冻结，必要时退役，不继续进入更深的决策消费层。

## 9. 后台记录与来源标注

一期的记录层不是单纯留日志，而是建设演化底座。至少应记录以下四类对象：

### 9.1 会话事实

- 原始对话内容
- 发言人
- 时间线
- 渠道与来源
- 阶段切换
- 转派、升级、结束等动作

### 9.2 系统判断

- 意图识别结果
- 情绪变化
- 注意力变化
- 压力状态变化
- 风险等级变化
- 建议分流目标
- 建议回复、摘要和下一步动作

### 9.3 来源与证据

每条关键判断或建议都应尽量记录：

- 来源类型
- 来源对象
- 版本信息
- 证据片段
- 触发时点

来源类型至少区分：

- RAG / 知识库
- 规则 / 策略
- 模型推断
- 人工标注 / 人工修正

当一个结论同时受多个来源影响时，一期采用“主来源 + 贡献来源”的归因模式：

- 主来源：回答这条判断主要由谁驱动
- 贡献来源：记录其他参与来源及其作用

贡献来源一期先记录简单角色，例如：

- 触发
- 支持
- 校验
- 覆盖

来源权重不写死在一期结构中，而是在后续反馈学习中逐步演进。

### 9.4 人工反馈与最终结果

- 坐席是否采纳建议
- 管理或质检是否改判
- 问题是否解决
- 是否升级、投诉、流失、续费
- 客户反馈
- 坐席反馈
- 质检结论

来源标注应作为一级能力建设，而不是附属备注字段。

反馈回写时，不只回写到结论本身，还应能挂接到主来源和贡献来源，为后续归因优化提供低噪声样本。

## 10. 从 0 数据到学习进化

学习闭环不应等系统成熟后再考虑结构，而应在一期就预埋基础挂点。

### 10.1 一期需要尽早搭建的闭环结构

- 样本回写点
- 人工修正入口
- 结果挂接关系
- 版本对比能力
- 来源追溯能力

### 10.2 一期暂不追求的闭环能力

- 不自动改规则
- 不自动更新策略
- 不让自动学习直接影响核心判断结果

因此，一期遵循的原则是：

`闭环结构尽早，闭环效果渐进`

## 11. 一期成功标准

### 11.1 验收指标分层

一期验收采用分层指标：

- 并列第一主指标：路由正确性、闭环可用性
- 第二层辅指标：辅助有效性

### 11.2 路由正确性

路由正确性采用组合指标，同时回答“对不对、稳不稳、需不需要改”：

- 人工标注一致率
- 同类样本稳定率
- 人工复核改判率

除量化指标外，路由正确性还要求路由结构本身具备可解释和可扩展特征，也就是：

- 路由节点和分流层级清楚
- 同类输入不会频繁跳变到不同路径
- 人能理解路由为什么这样运转
- 扩展规则、RAG 或模型后，路由骨架仍能保持稳定

### 11.3 闭环可用性

闭环可用性采用组合指标，同时回答“能不能跑、能不能查、能不能挂”：

- 链路跑通率
- 追溯完整率
- 反馈挂接成功率

闭环可用性同时要求记录结构具备后续进化能力，也就是：

- 过程数据完整
- 来源标注足够细
- 最终处理结果可回写
- 人工修正和反馈能挂回对应样本
- 后续能定位问题出在路由、上下文、知识、规则、模型还是交互策略

### 11.4 辅助有效性

辅助有效性作为辅指标，默认优先看：

- 复盘效率提升
- 异常发现提前量

建议采纳率可记录，但一期先放在观察位，而不作为主牵引指标。

辅助有效性除量化指标外，还要求辅助信息本身具备判读价值，也就是：

- 是否帮助坐席和管理者更快看懂当前会话阶段
- 是否更早发现风险、情绪、注意力和压力变化
- 是否减少人工重新翻找原始对话的成本
- 是否让建议和提醒具备可解释性

## 12. 一期核心风险

### 12.1 耦合风险

需要重点警惕：

- 数据结构和流程耦合
- 评估逻辑和界面耦合
- 路由决策和具体渠道或场景耦合

### 12.2 结构过于复杂

如果一期把事件、状态、指标、提示、来源、反馈全部揉成一个巨大复杂体，系统将难以理解、难以维护、难以扩展。

一期应优先追求结构可读、边界清楚，而不是元素堆满。

### 12.3 上下文有效性不足

需要持续关注：

- 当前轮上下文是否足够
- 阶段历史是否可保留
- 来源证据是否和当前判断相关
- 路由判断是否建立在有效上下文上

### 12.4 学习闭环建设失衡

如果学习闭环结构搭得过晚，后续反馈会无法挂接；如果过早追求闭环效果，又容易引入噪声。

因此，一期要尽早搭好闭环结构，但延后追求闭环自动优化效果。

### 12.5 配置失控与验证缺失

如果配置项不断增加却没有结构约束、测试约束和版本约束，配置本身会变成新的耦合源。

因此需要避免：

- 配置命名混乱
- 配置层级失控
- 配置变更没有验证
- 配置和 Spec 脱节

### 12.6 过早绑定具体客户端

如果一期过早围绕桌面程序、插件或生产坐席端展开，会把宿主系统、接入方式、权限模型和 UI 细节过早耦合进核心结构。

一期应优先验证服务能力和协议稳定性，再决定真实客户端的承载形式。

### 12.7 多租户与多校区返工风险

教培场景很容易涉及多机构、多校区、多课程线。如果这类隔离在骨架阶段未被考虑，后续返工成本会很高。

一期至少要验证：

- 基础数据隔离
- 配置隔离

### 12.8 查询与聚合层越权风险

多租户问题不只在存储层，也在查询接口、聚合接口、指挥台视图和复盘视图。如果这些消费层没有遵守默认最小可见原则，就很容易在多租户场景下发生越权。

## 13. 建议的一期实施顺序

建议按以下顺序推进：

1. 先定义核心结构
2. 再定义上下文模型
3. 然后定义配置模型
4. 再做关键独立信号的小样本可行性验证
5. 再定义 service 协议与对话模拟器
6. 再定义路由与评估机制
7. 再建设记录与反馈闭环底座
8. 最后做轻量控制台与提示策略

### 13.1 核心结构阶段

先确定：

- 路由骨架
- 评估层与辅助层边界
- 数据对象分类
- 来源对象分类
- 反馈闭环挂点
- 多租户最小隔离边界
- 角色模板边界

目标是命名正确、边界清楚。

### 13.2 上下文模型阶段

明确系统判断依赖哪些上下文：

- 当前消息
- 会话阶段历史
- 已触发事件
- 知识来源
- 人工处理痕迹

### 13.3 配置模型阶段

在进入路由和评估实现前，先定义配置模型，明确哪些变化点通过配置承载，例如：

- 路由配置
- 阈值配置
- 提示策略配置
- 来源策略配置
- 场景化展示配置

目标是先把可变部分和稳定骨架分开。

### 13.4 关键独立信号验证阶段

在正式固化协议前，先对少量真实或半真实样本进行小样本验证，重点看：

- 人工是否能对关键信号形成一致标注
- 草模或启发式规则能否稳定产出基础信号
- 哪些信号适合进入核心字段
- 哪些信号更适合先进入扩展区

这一步的目标是降低“协议先定死、信号后发现不可稳定产出”的返工风险。

### 13.5 Service 协议与模拟器阶段

在进入详细评估实现前，先定义服务协议和模拟器输入输出，包括：

- 带时间戳的对话事件流格式
- 基础会话元数据
- 评估输出结构
- 回写与反馈结构
- CLI 命令边界
- API 边界

这一阶段的目标是先稳定输入面和输出面，为后续 TDD 和闭环验证创造条件。

### 13.6 路由与评估阶段

明确：

- 路由分层方式
- 哪些节点适合规则化
- 哪些节点依赖模型或 RAG
- 哪些状态需要持续追踪
- 情绪、注意力、压力状态如何形成稳定结构输出

### 13.7 记录与反馈阶段

统一过程记录、结果记录、来源记录、人工反馈和版本信息，为学习闭环打底。

### 13.8 轻量控制台与提示阶段

最后再将结构翻译为：

- 轻量 Web 控制台中的回放、观察与复盘视图
- 管理与质检导向的全局态势视图
- 常规滚动提示与特别警告机制

## 14. 多租户查询与角色模板

### 14.1 默认最小可见

一期在查询与聚合层采用默认最小可见原则：

- 默认按租户隔离
- 跨校区 / 跨租户查看必须显式授权
- 隔离控制必须落实到查询接口、聚合接口、指挥台视图和复盘视图

### 14.2 租户内可见范围

在租户内部，是看到租户全局还是仅看到校区级，不写死在系统中，而由角色模板决定。

### 14.3 一期角色模板

一期先定义以下四类角色模板：

- 坐席 / 校区角色
- 校区管理角色
- 租户管理角色
- 平台审计角色

其中：

- 坐席 / 校区角色：默认只看自己职责范围内的会话与校区数据
- 校区管理角色：默认看本校区全局，但不跨校区
- 租户管理角色：默认看本租户范围内的全局数据
- 平台审计角色：一期默认只读，可跨范围查看，但不默认具备配置变更或改判权限

## 15. 工程方法约束

### 15.1 配置优先

工程落地时应优先采用配置优先设计，特别是在出现局部耦合时，先判断是否能通过配置抽离，而不是直接把局部判断写死在流程中。

### 15.2 Spec 驱动

整个实现过程应以 Spec 为驱动。结构、边界、配置模型、路由模型、提示策略和记录模型的落地，都应回到 Spec 中已有定义，而不是在实现阶段随意漂移。

### 15.3 坚持 TDD

在 Spec 驱动下坚持 TDD。每一类核心结构、关键路由、重要评估输出、配置解析和反馈回写，都应先定义验证方式，再进入实现。

TDD 在本项目中的价值主要体现在：

- 验证路由结构是否稳定
- 验证上下文组织是否有效
- 验证配置是否正确解耦局部变化
- 验证记录和反馈闭环是否真正跑通

### 15.4 闭环验证

一期不只是写出能力，还要确保闭环验证成立。也就是：

- Spec 能约束实现
- 测试能验证结构
- 回放能验证链路
- 反馈能验证闭环挂接

## 16. 一期定义总结

一期要建设的是一个面向教培在读服务场景、以离线回放为起点、以 CLI / API 优先的核心 service 为底座、以评估层与辅助层解耦为骨架、以轻量控制台承载观察与复盘、以可追溯记录为演化底座的内部坐席辅助系统。
